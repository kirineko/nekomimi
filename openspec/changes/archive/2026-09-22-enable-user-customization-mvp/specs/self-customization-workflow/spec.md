## Purpose

使安装后的 Nekomimi 能依据自身版本的开发资料，通过用户对话创建和修订定制能力，在当前会话验证并启用，且重启后持续可用，从而形成可验收的自定制产品体验。

## ADDED Requirements

### Requirement: 随包开发资料
系统 SHALL 在发布包交付匹配版本的 SDK 类型、文档索引、示例与能力声明，通过受限读取入口向模型提供；不得依赖源码 checkout、联网搜索或读取任意安装路径。

#### Scenario: 干净环境安装
- **WHEN** 用户在最低支持 Node.js 上安装 tarball 并请求添加命令
- **THEN** Agent 能发现和读取与已安装版本一致的示例和 API 契约，无需克隆仓库或放宽文件工具边界。

### Requirement: 校验与显式试运行
系统 SHALL 提供静态校验和独立的显式试运行，报告语法、SDK、注册冲突和缺失依赖；静态校验 MUST NOT 执行扩展工厂，试运行 SHALL 明确可信代码执行边界，并使用独立宿主状态及可替换工具/模型。

#### Scenario: 不良扩展校验
- **WHEN** Agent 创建语法错误或依赖缺失的扩展并发起静态校验
- **THEN** 得到可修复诊断，扩展工厂和工具未执行，现有有效配置不变。

### Requirement: 对话自定制闭环
系统 SHALL 支持通过对话创建项目扩展和 Skill、引用目录 Rules 与已配置 MCP、校验加载、执行自定义命令并显示 Web 贡献；修改后可在同一会话重载，重启后继续使用，停用后撤销其工具及专属提示。

#### Scenario: 创建并演进审查命令
- **WHEN** 用户要求创建 /review，读取 Git diff、应用检查清单和目标 Rules、使用 MCP 工具并显示审查状态，随后要求修改并重启服务
- **THEN** 每次实际执行使用对应启用版本，所有宿主调用与来源可追溯，重启不丢失资源；停用后新运行不再暴露该命令与工具，旧历史保留。

### Requirement: 第一版验收与第二版边界
系统 SHALL 以确定性端到端夹具验证创建、加载、执行、修改、失败、取消、重启和停用，并分别记录真实模型演练结果；V1 MUST NOT 将尚未支持的 V2 能力报告为已交付。

#### Scenario: 验收报告
- **WHEN** V1 准备完成并规划 V2 实施
- **THEN** 提供规格场景、浏览器与安装包验收结果及单独的真实模型演练记录，未完成项保留未完成状态，CI 无需真实凭证。
