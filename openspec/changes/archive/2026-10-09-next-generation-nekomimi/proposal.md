## Why

Nekomimi 已具备可观测执行、自定制与 Web 工作台，但当前基于 Pi 0.85.1 的运行时、单一主对话上下文和逐步叠加的界面结构，使跟进上游能力与区分“为用户做事”和“改变产品自身”越来越困难。需要在不承担旧版兼容成本的前提下，先完成统一规格，再分批重构为基于新版 Pi、拥有工作/创造双模式、可解释上下文和一致设计系统的下一代产品。

## What Changes

### 1. 变更性质、已确认范围与规划边界

- 本变更是产品级重构，不是依赖版本替换或局部 UI 美化；覆盖 Pi 接入、运行时边界、上下文、扩展开发及交付、Web 交互与验收。
- **BREAKING**：不要求兼容旧 SDK、旧配置、旧会话存储格式、旧内部接口或旧 UI 布局。新的契约可以删除历史兼容分支，不再以“双轨实现长期共存”为默认方案。
- 不兼容不等于允许删除用户资料。检测到旧存储时应明确版本不受支持并保留原文件，提供使用独立新目录的路径；自动覆盖、自动清空、静默迁移不属于本次授权。
- 先完成 proposal、delta specs、design、tasks，覆盖整个目标；之后按依赖顺序分批实现。提案完成不代表规格完成，规格完成不代表功能交付。
- proposal、delta specs、design 与 tasks 已建立；本轮按用户要求统一 Durable 目标并进入 apply。尚未确定的技术选型保留验证门槛，不用“待研究”替代用户行为契约，也不把候选技术当作已采用依赖。
- 核心方向已确认：工作模式服务用户项目；创造模式开发 Nekomimi 能力，扩展优先，必要时在隔离源码工作区修改核心，验证后再切换运行版本。

### 3. Pi 新版接入与持续跟进策略

- 以本次调研中官方 npm 已核验的 **1.0.4** 为首个候选基线，研究依据为 `reference/pi` 提交 `56b25ff4e`。该提交包含发布后变更，主分支存在不等于 1.0.4 tarball 已提供；实现前逐项核对发布包的 exports、类型及运行资产。
- 对 `pi-agent-core`、`pi-ai`、`pi-codemode`、`pi-mcp` 等分别建立“复用 / 保留产品适配 / 不引入”清单，并记录理由和验证结果。实际加入依赖的包以验证过的精确版本为准，不假设所有工作区包都已作为稳定 API 发布。
- 建立集中、薄的 Pi 集成边界。会话目标、授权、上下文来源和 UI 协议由 Nekomimi 定义；模型访问、可复用循环、工具脚本沙箱和协议基础设施优先使用 Pi 公开接口。
- 评估 `prepareRequest`、`finishTurn`、provider 事件观察、统一模型目录等新能力，优先替代现有可被公开接口覆盖的接入代码。provider 的已解析事件不能冒充原始网络证据。
- 不完整嵌入 Pi CLI，不把其 TUI、会话格式或内置扩展加载假设当作 Nekomimi 公共 API；SDK 是否自动加载 MCP/Codemode 必须实际验证。
- 建立版本升级契约测试：模型调用、工具轮次、取消、重试、错误终态、上下文注入、嵌套证据、发布包入口和安装后执行。未来升级由版本差异和这些测试驱动，而不是依赖“接口大致没变”。
- **BREAKING**：可移除为旧版 Pi 保留的绕行和映射，但不能删除仍用于 DeepSeek 协议保真、证据捕获或安全恢复的产品逻辑。

### 4. 运行时、Journal 与 Durable 的选择门槛

- 保持唯一权威历史，保留 `Journal -> ContextView -> WireRequest` 的责任区分；UI 与模型上下文均不是反向恢复执行事实的来源。
- `pi-durable` 1.0.4 是本变更的目标运行底座，通过公开 Harness、Storage、Registry、Models 与 hooks 接口适配并逐项验证，不再执行 A/B 自动回退。实验 API 的版本、能力与限制仍须明确记录。
- Journal 继续是唯一物理权威历史：Durable 的一批 StorageWrite 作为一个版本化 `durable.commit` 事件提交到 Nekomimi JSONL Journal，完整性附件先落盘；Durable 读取状态由这些已可靠提交批次重建，不另开原生 JSONL/SQLite session store。
- 公开 MemoryStorage 仅作可丢弃的读取投影和提交校验，先准备、再持久化、最后发布；失败使当前适配实例不可继续派发，重开仅从可靠 Journal 水位重建。内存不是第二份权威历史。
- 必须验证：同一提交决定任务、工具/模型结果与 UI 水位；每次网络 attempt 可捕获；产品固定上下文进入最终请求；原始流保留背压；取消、磁盘故障和 unknown 恢复有确定边界。
- 准入失败时补公开适配并记录阻碍，不静默回退低层 Agent、不牺牲唯一权威、不复制私有 reducer。技术切片通过不代表生产 Durable 已交付。
- 默认禁止自动重跑结果未知的工具。Pi 的 `replay: safe` 不能直接覆盖产品策略；是否允许特定无副作用任务恢复，须有独立、明确的证明和契约。
- 区分请求取消、执行停止、最终结果未知和终态持久化；进程崩溃、磁盘失败与网络断线不能被界面统一显示为成功或“已撤销”。
- 为新工作台需要的验证任务提供稳定任务 ID、归属、状态和取消入口。此范围不等于立即交付通用多代理编排或分布式调度平台。

### 5. 工作模式与创造模式

#### 工作模式

- 默认面向用户明确选定的项目与任务，加载项目/目录规则、适用技能、已启用能力及必要 MCP。
- 支持使用创造模式已经交付的工具、命令、主题和面板；使用能力不需要加载开发它的全过程。
- 默认不暴露 Nekomimi 自身开发、候选激活和核心版本切换工具，不常驻注入 SDK 文档或产品开发工作流。
- 用户提出产品定制请求时，可提供进入关联创造会话的入口；模型不能仅根据推断自行扩大工作区或执行权限。

#### 创造模式

- 面向明确的创造目标：扩展、Skill、Rule、工具、命令、Provider、MCP 配置、工作流、主题/面板，或核心源码变更。
- 明确展示目标宿主、目标能力、写入目录、应用范围、当前运行版本与候选版本，避免“改的是另一个全局安装”的混淆。
- 开发资料按当前宿主/SDK 版本发现和按需读取；普通扩展开发继续支持安装包内资料，不要求源码 checkout。
- 采用“需求 -> 候选 -> 静态验证 -> 独立试运行/预览 -> 授权应用 -> 宿主验收”的交付闭环。每一步记录具体版本和结果，预览成功不等于已经应用。
- 优先以扩展机制完成目标。核心修改需要独立源码工作区和可验证构建，不直接修改正在运行的安装目录；源码不可用、构建不支持或权限不足时明确阻塞，不偷偷退回原地修改。
- 核心版本切换需要运行边界、明确确认与失败保留旧版本的机制；不得热替换正在执行的工具实现。外部副作用和不兼容状态不能靠“回退代码”假装已撤销。

#### 模式交接与权限

- 推荐以关联的独立会话承载两种模式，分别拥有历史、草稿、上下文预算和有效能力集；不是对同一 messages 数组换一段 system prompt。
- 交接只携带选定目标、相关引用、约束、交付物及验证摘要，保存源/目标会话和内容版本；不默认复制全部项目源码或完整开发历史。
- 工作会话接收已交付能力的使用说明及证据索引，不吸收所有 SDK 文档、构建日志和失败尝试。
- 进入创造模式本身不构成授权。原项目规则不自动升级成产品规则，创造目录也不自动获得用户级写入或任意 shell 权限。
- 模式、工作区、授权是独立维度；仅改变 cwd 或隐藏工具不能宣称构成系统级沙箱。真实可写边界与可信扩展边界必须在设计和 UI 中说明。

### 6. 上下文管理重构

- 将上下文构建从提示词拼接和会话遍历中提升为独立、可测试的请求前服务；每次请求固定模式、目标、模型、有效能力版本和上下文 revision。
- 分层组织稳定宿主规则、模式指导、工作区规则、有效工具指导、按需技能/资料、任务历史和当前动态事实。每层有来源、作用域和内容版本。
- 区分“可发现”“曾读取”“当前有效”“本次实际注入”“仅作为历史证据保留”。UI 不再将工具可用或技能曾加载等同于本次已发送。
- 默认先降低不必要输入：按需发现工具和文档、大结果转为持久证据引用、只传回必要摘要；不是等上下文塞满后统一摘要。
- 为工作/创造会话分别计算预算。预留模型输出、工具结果和摘要开销，模型或 schema 改变时重新估算，不能沿用另一个模型的使用锚点。
- 压缩只作用于可闭合、可追溯的历史区间；保留当前约束、未完成任务、待授权事项、未知工具结果和关键交付状态。失败、取消或来源冲突不覆盖有效上下文。
- 跨模式交接摘要与普通压缩是不同用途的模型任务，使用独立指令和记录；不会执行摘要里的历史指令。
- 缓存友好是优化目标而非正确性前提。权限撤销、规则更新与模型能力约束优先；不将前缀 hash 相同描述为服务端缓存命中。
- 上下文检查器解释加入、排除、裁剪、摘要和替换的原因，并能定位到最终请求与原始证据。

### 7. Codemode、工具发现与 MCP

- 接入 Pi Codemode 能力，使模型可编写受限 JavaScript 组合、并行和过滤工具结果，减少多次模型往返与无关输出进入上下文。
- 所有嵌套工具仍经过统一校验、授权、意图持久化和执行记录入口，拥有独立调用 ID 和父调用关联；沙箱入口不能成为绕过门禁的第二条执行路径。
- 脚本输出、模型可见结果、UI 展示与完整子调用证据分离。失败脚本保留已经完成的子调用证据；取消未完成调用不等于撤销已经发生的副作用。
- 工具并发由能力和目标决定。同一文件变更需要序列化和新鲜度保护，不能因为 Codemode 支持 `Promise.all` 就放开所有写入竞争。
- 明确沙箱的内存、输出、时间、持久小状态和取消边界；代码运行隔离不等于被调用 shell、MCP 服务或可信扩展自动被隔离。
- MCP 采用直接暴露、按需发现、脚本调用和隐藏的清晰策略；大量工具不再全量进入请求，非必要服务器连接不阻塞普通任务首轮。
- 工具发现只改变可见性，不增加授权。工具名规范化、重名处理、版本固定、停用撤销和恢复后可见性必须有确定行为。
- 保留资源、模板、OAuth、结构化错误和凭证隔离要求。为复用 Pi MCP 而改变底层实现之前，应验证它对现有协议能力的覆盖；缺口必须显式保留适配或进入规格决策，不能静默丢弃。

### 8. 模型能力与调用证据

- 统一主对话、压缩、命名、交接、扩展辅助调用、分类与图片生成的宿主记录入口；各用途使用独立上下文并关联外层任务。
- 接入 Pi 多类型模型目录时区分 chat、classifier、image。向用户展示的可用能力取决于版本、凭证和已验证适配，不是目录里出现名称就宣称可用。
- 分类和图片生成为新版模型能力接入范围，但不强制成为普通工作任务依赖；错误或缺少凭证时明确不可用，不隐式切换付费服务。
- 评估虚拟模型注册和路由接口。若落地，用户所选策略与实际执行的物理模型必须分别记录，路由自身的辅助模型费用也要关联。
- 不预设自动路由为默认行为，不在本阶段承诺分类器提高质量或降低成本。先验证记录、能力检查、重试和上下文窗口变化，再决定默认产品入口。
- 保留已验证的 DeepSeek Responses 行为。更换 Pi Provider 或改用其他协议需要明确验证，不因上游默认采用 Chat Completions 就静默改变既有请求语义。
- 解析前原始流、最终 body、逐次 attempt 与归一化消息是不同证据层；任何缺失都明确标记，不以新的便利事件 API 替代旧的保真要求。

### 9. UI 全面重构与设计系统

- **BREAKING**：重构信息架构、导航、页面布局、组件契约和主题接口，不保留旧弹窗布局或 CSS 选择器兼容。
- 保留 React、TypeScript、Vite 作为候选基础，不引入无产品需求支撑的 SSR 服务端框架。推荐验证以下组合，实际依赖版本和最终选择在 design 中固定：

| 层 | 推荐候选 | 验证重点 |
| --- | --- | --- |
| 组件与交互基础 | shadcn/ui + Radix | React 版本兼容、焦点、弹层、键盘和控件组合；纳入项目的组件代码也需要维护 |
| 样式 | Tailwind CSS + 语义设计 tokens | 主题覆盖、字体与素材、减少动效、样式隔离、生成产物与许可证 |
| 服务端状态 | TanStack Query | 快照读取、错误恢复、缓存失效；写操作不可自动重复，不能取代权威事件序列 |
| 路由 | TanStack Router | 双工作台、深链接、恢复选中目标、导航期间的草稿保留 |
| 大列表 | TanStack Virtual | 流式内容、高度变化、分页锚点、代码块和图片、键盘阅读 |
| 布局 | 可调整分栏组件 | 最小宽度、布局持久化、窄屏替代、辅助技术和焦点顺序 |

- 工作工作台：项目/会话导航、任务输入与时间线、文件/变更/结果侧栏；上下文、费用和执行证据按需展开但始终可到达。
- 创造工作台：能力/核心候选导航、创造会话、预览/差异/验证侧栏；清楚显示草稿、验证中、验证失败、待授权、待应用、已应用及宿主验收状态。
- 两种工作台共用身份、模型选择、运行/停止、通知、连接状态和证据组件，避免复制两套产品基础交互。
- 模式、目标项目、目标宿主和生效范围在核心操作附近可见；不要只通过背景颜色提示当前写入对象。
- 建立字体、间距、层级、颜色、圆角、图标、状态和动效规范。保留 Nekomimi 轻量猫系品牌方向，但具体配色、密度和视觉样稿需后续评审，不把库默认主题直接视为完成设计。
- 使用组件级状态、页面草稿、服务端查询和持久会话流的明确分工。轮询或重连不应覆盖未提交输入、抢焦点或重复触发 mutation。
- 保留主题与扩展 UI 能力，重新定义稳定 tokens、插槽和交互桥。扩展不得覆盖宿主授权、停止、恢复等关键控件；历史阅读无需执行扩展。
- 验收覆盖键盘、可见焦点、360px 窄屏、200% 缩放、减少动效、空/加载/失败状态、长列表、自动跟随和历史滚动锚点，而非只提交静态截图。

### 10. 分批交付顺序与验收方向

完整 delta specs、design 和 tasks 应先建立，再实施以下批次。批次是依赖与验收边界，不是提前声明的完成状态；独立部分可并行设计，但不能跳过其前置技术门槛。

| 批次 | 范围 | 退出条件 |
| --- | --- | --- |
| 0：选型验证 | 1.0.4 发布包公开入口；Durable 单提交与恢复门禁验证；Codemode/MCP 证据接入；UI 组件切片 | 形成可复查结果，明确采用与拒绝的路线，更新 design/specs；未知项不得被默认视为通过 |

| 3：能力层与创造闭环 | Codemode、MCP 按需发现、新版 SDK、候选验证、受控应用、核心修改候选 | 创建/修改/验证/取消/失败/应用/回退各有版本化证据；工作会话能使用交付结果 |
| 4：新工作台 | 设计系统、路由与状态管理、工作和创造页面、预览及上下文/证据检查 | 两种工作台端到端可用；长会话、重连、草稿、焦点和可访问性验收通过 |
| 5：整体验收 | 新安装、旧目录保护、安装包资料、综合场景、性能与真实模型抽样 | 无源码安装闭环、确定性测试和发布包检查完成；实测与模拟、已验证平台与未验证平台分开记录 |

UI 设计系统原型可在批次 0 验证，页面实现可在服务契约固定后启动，不需要等待所有能力完成才开始视觉工作。任何批次完成都不自动授权发版，也不应在总变更未完成时整体归档。

#### 跨批次最低验收场景

1. 工作模式修复普通项目：只加载该项目所需上下文，不出现产品开发管理工具；查看任意调用可追溯实际输入。
2. 从工作模式发起新增审查能力：在关联创造会话开发，独立校验并应用，返回工作会话使用；失败日志与 SDK 正文不全量污染工作历史。
3. 创造主题/面板：独立预览通过但未授权时保持旧 UI；应用、刷新、禁用及回退结果与实际版本一致。
4. 核心修改：在隔离源码工作区形成候选并构建；失败、取消或未确认切换不影响正在运行的安装。
5. Codemode 部分成功后失败：成功子调用、未知子调用、脚本错误分别可检查，后续恢复不重跑已发生副作用。
6. MCP 服务迟到或断线：普通工作可继续，发现和调用失败可诊断；重连和工具列表变化不篡改历史请求。
7. 长创造会话压缩及交接：保存约束、候选版本、待授权项与未知结果，仍能追溯被摘要内容，不能只保留“已经做完”的乐观摘要。
8. 浏览器掉线、双窗口、重复 commandId、进程重启和磁盘失败：没有重复写入或未授权恢复；界面显示真实可靠范围。
9. 分类、图片生成或路由调用失败：保留用途、attempt、费用及外层关联；不能作为隐藏模型调用绕过记录。
10. 没有旧版兼容适配的新安装与遇到旧数据目录两条路径：新环境可用，旧数据不被静默修改。

性能验收先建立相同模型配置、上下文、工具和机器条件下的基线，再制定阈值。记录首轮声明/schema 体积、上下文估计、请求准备时间、长列表响应、内存与恢复时间；服务端缓存命中、任务完成率和真实费用需要真实模型证据，不由模拟测试推断。

### 11. 非目标与后置范围

- 不在本变更中发布版本、创建标签或上传 npm；发布需独立明确授权。
- 不提供旧 SDK、旧存储、旧主题接口的自动兼容层，也不承诺无损自动迁移旧会话。
- 不建设云端多租户、团队协作、跨设备同步、市场服务端或完整 IDE。
- 不将 Pi 所有功能逐项照搬；TUI 全面实现、通用子代理编排、自治自我升级及默认自动模型路由不作为本轮必交付目标。
- `pi-env`/SSH 远程执行仅作为执行环境接口的后续参考，本轮要求的是本地隔离创造工作区，不承诺远程 daemon 部署。
- 不把可信扩展或 unrestricted shell 描述为安全沙箱；不把前端隐藏当作权限控制。
- 不预先承诺 token 降幅、缓存收益、性能倍数或模型成功率提升。

## Capabilities

以下能力清单是后续 delta specs 的范围合同。每个条目均需对应规格文件；保留但未改变行为的既有能力作为回归约束，不另造同名替代规格。

### New Capabilities

- `pi-platform-integration`: Pi 发布版本与公开接口的集中接入、能力检测、版本诊断及升级契约验证；拒绝静默使用主分支专属能力。
- `work-create-modes`: 工作/创造模式的身份、目标、工具集、作用域和权限边界；模式持久化及恢复，不把模式视为授权。
- `mode-session-handoff`: 两种模式间的关联会话、明确输入选择、交接产物、来源引用、独立草稿与取消/重复提交语义。
- `context-selection-policy`: 请求级上下文选择、分层输入、按需发现、预算、排除理由与当前有效状态；与原始证据、压缩、最终协议投影的接口。
- `codemode-execution`: 脚本沙箱、嵌套工具调用、并发约束、输出投影、小状态持久化、部分失败及取消证据。
- `core-change-candidates`: Nekomimi 核心源码的隔离开发、版本匹配、候选构建和验证、受控运行版本切换及失败恢复。
- `model-operation-catalog`: chat/classifier/image 能力发现、配置与不可用诊断，统一宿主调用入口；实验性虚拟路由的能力边界。
- `web-design-system`: 共享基础组件、语义 tokens、双工作台布局、响应式与可访问性、主题故障回退及一致的加载/错误/状态表达。

### Modified Capabilities

- `execution-journal`: 增加模式、关联会话、候选及嵌套调用的稳定因果标识，明确新运行底座的唯一权威及旧格式拒绝边界；保留意图先落盘和未知结果不重跑。
- `model-call-evidence`: 扩大用途到交接、分类、图片及可能的路由调用，区分用户模型选择与实际派发；仍要求逐 attempt 的最终请求和响应证据。
- `prompt-task-profiles`: 将主对话拆为工作与创造配置，增加交接用途，明确各用途独立指令、版本和无关流程排除。
- `prompt-context-provenance`: 记录模式、目标、选择/排除理由和交接引用；区分可发现、已读取、有效及实际注入，保持禁用撤销与旧证据不变。
- `context-compaction`: 面向独立模式上下文及版本化交接保留约束、候选和未知结果；明确输入 revision、模型变化和失败不生效。
- `context-occupancy`: 为模式、模型和有效能力快照计算容量与预算，区分估计、上游 usage 和实际缓存数据，向检查器提供分层占用。
- `session-lifecycle`: 新会话拥有模式与目标身份，关联会话的创建、命名、取消和删除范围明确；不以进入另一个工作台触发执行。
- `extension-runtime`: **BREAKING**：重整 SDK 与 Pi 适配边界，统一直接/嵌套/辅助模型执行门禁，不要求旧 SDK 兼容，保留可信代码和进程隔离边界。
- `customization-development`: 创造模式成为开发入口，明确扩展与核心修改的选择、宿主版本、独立验证及安全运行边界。
- `customization-lifecycle`: 增加创造任务与工作交付的关联，候选/活动/验证/应用状态在两个工作台一致，应用范围不得随模式切换扩张。
- `self-customization-workflow`: **BREAKING**：将混合会话自定制调整为关联创造会话与显式交付；安装包资料与普通扩展离线开发继续可用。
- `mcp-tool-integration`: 增加工具暴露策略、按需发现、延迟连接、Codemode 调用与嵌套证据，保持结构化结果和取消/断线语义。
- `mcp-context-and-auth`: 将资源与模板纳入模式化上下文选择，验证 Pi MCP 复用后的 OAuth 及凭证作用域，不把发现、登录或模式切换视为新的执行授权。
- `web-task-workbench`: **BREAKING**：以工作/创造双工作台替代单一页面布局，保留输入、停止、历史、文件/变更、错误恢复和稳定焦点等用户能力。
- `web-customization`: **BREAKING**：管理弹窗演进为创造工作台及能力管理视图，模型配置、权限、候选和高级诊断重新组织，保留明确交付阶段。
- `runtime-ui-extensions`: **BREAKING**：更新主题 tokens、插槽与桥接契约，区分工作和创造适用区域；保留受控交互和不可覆盖的宿主关键控件。
- `web-session-stream`: 新工作台消费同一权威快照与增量，显式绑定模式/目标/订阅身份，导航或重连不重复提交，慢客户端可安全恢复。
- `web-evidence-inspector`: 展示模式化上下文、交接链、嵌套工具树和多类型模型用途，将完整执行证据与简短会话展示分开。

## Impact

### 代码、依赖与接口

- 运行与模型：`src/runtime.ts`、`src/provider.ts`、`src/recorded-call.ts`、`src/customization/adapter-provider.ts`；预计集中 Pi 类型和生命周期适配，具体目录结构留给 design。
- 历史与上下文：`src/journal.ts`、`src/context.ts`、`src/prompts.ts`、`src/compaction.ts`、`src/context-meter.ts`、`src/storage/`；新 schema 可破坏兼容，但不得降低证据完整性。
- 能力与创造：`src/customization/`、`src/extensions.ts`、`extension-docs/`；减少重复实现，重定义 SDK/候选/模式接口，公开示例与打包资料同时更新。
- 服务与协议：`src/server/`、`src/shared/protocol.ts`、`src/projection/`；引入模式、目标、交接、任务及新视图契约，浏览器不直接依赖 Pi 内部消息类型。
- Web：`src/web/` 的路由、hooks、组件、主题与样式体系整体重组；静态资源仍支持随安装包交付，不要求独立云服务。
- 包与构建：`package.json`、`package-lock.json`、构建配置、安装包验收；新增沙箱运行资产、样式构建和组件依赖需检查体积、来源、许可证及最低 Node 运行时。
- 测试：更新 unit、protocol、browser、pack fixtures，增加强制终止、模式交接、工具嵌套、旧目录保护和核心候选切换场景；先复用现有风险用例，再调整其接口，不能只更新快照使其通过。

### 既有规格冲突与保留保证

- 当前 `spec.md` 中“框架仅拥有循环”的选型与本提案更大范围复用 Pi 存在变化；这是有门槛的重评估，不是已决定由 Pi 接管所有状态。
- 当前原始 JSONL 作为权威存储的约束继续有效，Durable 若要求改变该点必须显式形成后续设计与规格修改，不能通过实现绕过。
- 既有 V1/V2 SDK、旧纯文本候选等兼容承诺与“不考虑旧版兼容”的新方向冲突，应在相关 delta specs 中明确替换或删除，不保留含糊的双重承诺。
- 旧“同一会话开发并启用”和以定制弹窗为中心的交互需要改变，但能力应用、失败保留旧版本、离线资料和真实宿主验收保证继续保留。
- 原始请求保真、工具新鲜度保护、凭证排除、回放无副作用、未知结果不重跑、只展示真实验证状态等不是兼容负担，不因重构移除。
- 历史 `spec.md` 中的阶段状态与现行主规格可能不一致；本次以主规格和实际代码作为现状依据，历史研究仅用于追溯取舍，不把早期“未交付”描述直接当作现在事实。

### 待验证决策与风险控制

| 决策/风险 | 必须取得的证据 | 未通过时的处理 |
| --- | --- | --- |
| Pi 1.0.4 与当前 adapter 的兼容 | 发布 tarball 的类型/exports、工具续轮、原始流、请求 body、取消和重试对照 | 保留必要 adapter，禁止用静默协议降级换取编译通过 |
| Durable 目标底座的生产准入 | 唯一持久化提交边界、逐 attempt 证据、可替换上下文、崩溃和未知工具结果用例 | 补公开适配；无法满足时阻止相应能力交付并报告阻碍，不自动回退 Agent |
| Codemode/MCP 是否能复用完整执行管线 | 子调用授权、先落盘、部分成功、取消、返回结构和版本撤销测试 | 补公开适配或缩小接入能力，不暴露绕过管线的调用 |
| 两模式隔离是否真实有效 | 工具清单、最终上下文、工作区目标和写权限对照；跨模式误用场景 | 阻止跨域操作并提示交接，不能依赖模型自觉 |
| 前端组合是否适合现有运行环境 | 真实组件切片、流式长列表、主题预览、键盘和窄屏试验 | 在 design 中更换候选并说明，不绑定未经验证的库版本 |
| 核心候选切换是否可安全交付 | 源码/构建身份、独立启动、活动任务处理、切换失败和回退场景 | 该批次保持未完成；只报告候选已生成，不宣称核心修改已应用 |
| 新架构是否降低上下文与维护成本 | 可复现基线、相同场景的新旧请求对照、依赖/适配面分析 | 如实记录无收益或回归，调整设计；不伪造性能与完成率提升 |

所有验证结果应绑定版本、环境和命令。无凭证 CI 验证结构和行为边界；真实模型测试单独记录费用、随机性和失败，不成为普通 CI 的前提。总体设计评审前不开始依赖升级或 UI 实施，全部验收完成前不将本变更归档为已交付。
