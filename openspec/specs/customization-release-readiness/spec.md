# customization-release-readiness Specification

## Purpose

定义 V1 与 V2 合并后的可交付产品门槛，使原始自定制需求有实际使用证据，并把兼容迁移、安装包、真实演练与公开发布状态清楚区分而不以规划完成代替交付。

## Requirements

### Requirement: 原始需求全覆盖

系统 SHALL 在干净安装中支持通过对话创建并实际使用命令、工具、Provider、工作流及 UI 定制，并组合 Skills、Rules 与 MCP；每类能力均须有确定性验收和可检查的运行证据。

#### Scenario: 完整审查能力包
- **WHEN** 用户要求创建审查命令、检查工具与 Skill，应用目录规则、MCP 内容、自定义模型和审查面板
- **THEN** 生成、修复、激活、实际使用、暂停恢复、更新回退、分享重装和停用均可验证，不需要修改产品源码。

### Requirement: 兼容与故障门槛

交付版本 SHALL 验证当前 SDK 3、配置、状态与历史契约，以及取消、崩溃、越权、未知副作用、依赖缺失和升级失败。对不支持的旧 SDK/数据格式 SHALL 验证工厂及写入前拒绝、来源诊断和原件内容不变，不承诺 V1/V2 自动升级或运行兼容；受支持历史的只读观察不能被解释为允许继续执行。未通过的必需场景 SHALL 阻止把对应新能力标记完成。

#### Scenario: 旧项目升级
- **WHEN** 一个包含不受支持旧扩展或配置格式的项目选择新版宿主
- **THEN** 宿主拒绝执行旧工厂或改写旧配置，说明不支持的契约并指引独立新数据目录；旧文件及摘要保持不变，不以自动迁移或部分加载伪装兼容。受支持历史只能按观察/恢复的独立准入规则读取或显式继续。

### Requirement: 真实模型证据

系统交付验收 SHALL 单独记录真实模型对话生成、失败修复和实际使用结果，包含模型标识、耗时、attempt、限制及失败；模拟服务不能冒充真实调用，真实账户不成为 CI 前提。

#### Scenario: 模型生成候选失败
- **WHEN** 真实模型生成类型或注册错误并进入修复流程
- **THEN** 保留失败与修复证据，成功使用必须实际运行；若只有预置故障则明确标识，不伪造首次生成失败或统计成功率。

### Requirement: 可安装版本候选

交付 SHALL 提供一致版本的类型、SDK 文档、示例、构建产物、迁移/发布说明和 tarball，验证 Node.js 22.19.0/24.15.0 的 macOS/Linux 运行、扩展进程/MCP 清理和 Web 冒烟；不得用平台推测替代必需验收。当前 Windows 优化及原生安装验证 SHALL 按发布契约明确暂缓，不创建 Windows CI job，不将 macOS/Linux 或模拟路径结果宣称为 Windows 支持；后续恢复须通过独立变更及原生验收。

#### Scenario: 离线账户独立安装验收
- **WHEN** 在干净环境安装最终候选 tarball，使用本地模型/MCP/OAuth fixture
- **THEN** 公共 SDK、能力包、模型回合、工作流恢复和 Web 可使用，验收不用真实账户，报告记录包完整性与平台。

### Requirement: 发布状态区分

系统交付记录 SHALL 区分候选已验证与 registry 已发布；公开发布按既有标签 CI 和正式 Release 流程执行，未经真实核验不得报告已发布。

#### Scenario: 候选完成但未上传
- **WHEN** 本地 tarball 验收完成且用户尚未要求公开发版
- **THEN** 交付候选与验证记录，保持未发布状态，不自动创建标签或正式 Release。
