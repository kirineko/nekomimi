# 10.8 核心切换与恢复界面验收

2026-10-08，macOS arm64 / Node.js 24.15.0 / Chrome 154.0.8037.98。未提交工作区，基线及文件摘要见 manifest。任务 10.8 完成，总进度 77/89。

## 实现与契约

- 核心候选的“构建与验证记录”提供版本切换入口。先读取并核验计划，再在对话框显示当前/目标构建、候选与验证 ID、产物摘要、工作区和数据目录、协议及 planHash。取消为初始焦点，Escape 返回审阅按钮；确认后焦点回到切换区域。
- 只读状态持续刷新，忙碌阻碍有任务类型、状态和对应会话入口，可等待或进入会话处理；真正切换仍通过既有保留锁及业务门禁重新核对。没有强杀或热迁移路径。
- 请求前在浏览器会话存储保存按宿主/会话/候选隔离的确认身份，失败后只查询原 commandId。明确重试复用完整原命令；已接受 unknown 不重发。回执校验 commandId、planHash、状态与实际构建，其他命令的回执不能变成成功证据。
- 成功提示同时要求持久 applied 回执、当前实际运行目标 build 和相同安装。状态读取失败隐藏旧身份，不把历史 applied 当作当前运行状态。
- 顶部“版本恢复”独立于原候选页面：旧核心会话因切换后身份改变不可读时，仍能读取保存命令与安装恢复信息。显示最后/前一个 confirmed selection、未完成意图和进程观察；这些历史选择不等于运行中的进程。
- 新增 `/core/recovery` GET 经认证和托管 IPC 读取正确安装，不取得 writer、不发送停止信号、不对账或启动。恢复对账及启动仍由同一安装 CLI 按新计划明确授权；源码入口不伪造可执行恢复命令。
- 普通启动方式只提供 `/sessions/:id/core-launch-info?buildId=...` GET。先检查会话模式、目标归属及构建记录，再复核当前构建，返回准确 argv；失效构建返回明确 `409 core_conflict`。不修改 PATH 或全局安装，不报告已应用。

## 真实执行与模拟边界

`test/browser/core-switch-real.spec.ts` 将同一已编译服务复制为两个目录，向第二个目录加入独立身份标记并重新计算构建摘要。浏览器通过真实认证 HTTP → 托管 IPC → supervisor 切换；两个实际 Web 子进程 PID 不同，新服务沿用端口，记录唯一切换意图和终态，实际身份与回执匹配。刷新后即使原候选页面返回 host_changed，独立恢复入口仍读取该回执及前后选择。最后确认端口关闭，安装 Journal 不含浏览器令牌。

此浏览器测试的源码/构建/独立验证准入及候选显示目录使用明确夹具，依赖从仓库解析；它不是第二次完整 npm 构建或无源码安装包验收。完整构建准入、包验收及平台矩阵仍分别属于既有第 8 节证据和第 11 节最终门槛。普通 UI 场景使用真实 CoreSwitches、Journal 和 HTTP，替换结果由测试运行时模拟；实际失败回退/存储拒绝另由 core-rollback 单元集运行真实子进程验证。
