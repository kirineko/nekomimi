# web_fetch 代理与通用兼容验收

日期：2026-09-16。环境：macOS arm64 / Node.js 24.15.0；变更 `support-web-fetch-proxy`。

## 范围

- 环境 HTTP(S) 代理和 macOS/Windows 启用的系统静态代理；无代理直连，支持专用覆盖及 NO_PROXY。
- 代理路由先于本机 DNS；直连继续固定公开地址。代理负责远端 DNS/访问控制，不声称客户端能验证其最终解析地址。
- Deepy 浏览器请求头、通用挑战标志、原有压缩/编码/正文与摘要回退。不包含网站特化。

## 确定性验证

- 策略覆盖：显式直连/代理、环境变量大小写和优先级、系统静态开关、无代理、绕过列表、PAC/SOCKS 拒绝及默认自动发现开关。
- 平台检测以进程替身验证 macOS/Windows 输入解析、2 秒限时、输出上限、取消和错误信息脱敏。
- 真实本地 HTTP CONNECT 代理验证域名交给代理、不调用本机 Fake-IP DNS、请求头最终值、gzip 解码及元数据回退；代理认证不出现在目标 HTTP 请求。
- 代理失败不回退直连；NO_PROXY 仍拒绝非公开 DNS；本地 IP/域名拒绝；同源重定向逐跳记录，跨源不自动跟随。
- 普通 403 与 cf-mitigated: challenge 的 HTTP 200/403 分别分类；保存脱敏证据，导出扫描没有代理密码和 Basic token，导入回放不增加请求。
- 百分号转义与空密码代理认证、挂起代理请求超时和取消均有回归。
- 浏览器验证失败卡片、HTTP 状态、模型收到的错误及重载不重抓取。

## 现场验证

通过应用默认 webFetch 配置（未注入 transport/代理地址），自动读取本机已启用的系统代理。`https://example.com/` 返回 HTTP 200、正文 559 字节，route 为 proxy/system；这证明实际 HTTPS CONNECT、TLS 验证、系统代理发现与正文提取链路可用。

同轮另两个目标出现经代理连接失败和 HTTP 404，均正确记录为失败，没有自动重试、修改 URL 或回退直连。目标可达性和网站状态随出口/时间变化，不以单次 HTTP 成功承诺所有网站可访问。现场 Journal 存于本机临时目录 `nekomimi-proxy-live-g8PVaM`，未将用户会话或代理配置提交到仓库。

## 验证限制与过程

Windows 系统代理使用 fixture 验证，尚未在 Windows 实机调用；未执行 PAC/WPAD/SOCKS，未使用真实模型、浏览器登录态或付费抓取服务。仅开启自动发现而未提供具体静态代理或 PAC 地址时视为无代理。

首轮直接运行 Vitest 时此前清理的 dist 尚未重建，依赖已编译 CLI 和静态资源的测试失败；重建后原有完整测试通过。另一并行变更的 OpenSpec 产物曾短暂未完成，随后全量严格校验通过。本次未修改该变更。
