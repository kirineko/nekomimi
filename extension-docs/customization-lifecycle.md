# 从定制需求到实际效果

先调用 `customization_sdk`，再按需要读取 `public`、`ui` 契约。返回的 `host.build` 和 `host.contract` 标识正在处理任务的宿主；不要用 PATH 中另一个 `nekomimi` 安装的检查结果判断当前宿主。`resource_list` 是本轮固定快照；开发后的最新状态请调用 `customization_status`，可用 `resourceId` 限定输出。

## 先确定作用域

默认项目级；用户明确要求跨项目时使用用户级资源或包。查询 SDK scopes 获取实际路径，参见 [作用域指南](scopes.md)。候选开发目录仍属于项目，不能把用户级安装与当前主题选择混为一谈。

## 创建主题

1. 用 `customization_candidate` 的 `create` 创建 `theme` 模板，编辑返回的目录。字体使用 WOFF/WOFF2，背景使用 PNG/JPEG/WebP；保持原始文件字节，不把二进制内容当作文本写回。
2. 调用 `inspect`。结果是静态类型检查和文件差异，不代表工厂执行、权限通过或宿主效果完成。修改任何源码或素材后重新检查，使用新的 `contentHash`。
3. 打开定制能力的“我的定制”。选择对应候选，检查新增权限后明确确认授权。资源内贡献共享资源授权，不是分别隔离的沙箱。任务运行时加载会排队。
4. 用 `customization_status` 查看实际加载状态。主题加载后仍需“预览与应用”；预览取消不会覆盖已保存选择。
5. 应用后检查浏览器实际字体、颜色、间距、气泡及动效。宿主已应用和视觉是否符合用户意图是不同层面的判断；不要把静态通过或预览成功写成完整验收。
6. 用同一资源的 `customization_status` 输出交付卡，说明已完成阶段和下一步。历史卡只打开当前管理状态，不自动执行旧版本。

## 已有面板新增主题

保留原 `commands/panels/ui` 声明，添加 `themes`，通过 `registerTheme` 注册主题；按需附带字体和图片。修改旧文件并不会自动扩展原授权。

“我的定制”会显示缺少的权限。用户检查差异后确认，服务端同时检查内容版本和授权设置版本；任一变化都应重新检查，不自动重试。连续执行 reload 无法代替授权。加载失败保留旧活动版本；等待任务结束不等于已经切换。

成功加载主题之后再预览和应用。遇到空主题列表，先查询 `customization_status`，不要读取浏览器 API 令牌、创建临时空宿主或推测内部配置文件。

## 配色

颜色接受 `#RGB`、`#RGBA`、`#RRGGBB`、`#RRGGBBAA`、`rgb/rgba`、`hsl/hsla` 和 `transparent`，宿主与面板统一归一化。浅粉、白底或低对比度不会被拒绝，也不会被擅自加深。CSS 变量、URL、表达式和无效数值仍不接受。

预览可取消；即使选了难读的颜色，也可用键盘打开“更多操作 → 外观 → 恢复默认界面”。扩展不接管此宿主恢复入口。

## 目录与证据

“我的定制”支持本会话、当前项目、用户级和全部范围，以及能力类型筛选。受控创建和关联更新记录来源会话；外部编辑和旧资源不能确定作者时显示来源未知。来源不影响内容摘要，删除会话不会删除能力。

管理页保留资源、包、候选、MCP、工作流及高级操作。静态检查反馈属于具体资源和版本；加载历史默认折叠。SDK/工具返回的技术数据供开发定位，用户交付应优先展示可操作结果。

候选可用 `customization_candidate` 的 `export` 导出原始源码与素材归档，传入 `id`、检查后的 `contentHash` 和工作区内的新 `output` 路径。已有目标不会被覆盖；需要可安装能力包时仍使用包含 `nekomimi.json` 的能力包格式。
